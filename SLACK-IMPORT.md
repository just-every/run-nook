# Slack export ZIP import

Nook reads the archive on your device. Source authentication stays there; only
the reviewed normalized history and selected files are uploaded. Choose the
source namespace and mappings, use **Preview exact import**, accept the named
omissions, then choose **Create dry run**. Review the door's counts, rejections
and differences before **Apply reviewed plan**. A dry run expires after 30
minutes. If an audience or source changes, create a fresh dry run. The history
provides status, reconciliation and guarded Undo, including imports made before
the shared door. A native edit or later work refuses destructive undo.

For another snapshot of the same workspace, keep its source namespace and select
**Compare with the previous import in this source namespace**. Unchanged records
stay in place; source records absent from the new snapshot remain in Nook.

Business imports use the same door. The owner can enable them in Import history
and permanently revoke signing keys; switching access on again keeps revocations.
Workspace archives retain import batches and custody; restoring an archive
leaves Business imports disabled.


The importer runs in the emitted Worker on local D1 and R2.

The automated `tests/pilot-journey.mjs` is part of `rer verify`. At 1440px and 390px it exercises a fresh local RER setup, owner and independent teammate sessions through the local dev entry, a private file, and a six-channel synthetic corpus: 40 directory actors, 5,000 source messages (3,500 content and 1,500 system notices), 499 supplied files and one explicitly missing file. It checks complete history, thread and file censuses, audience access and revocation, zero native unread/attention/mail from import, populated undo and the guard after later live work, then a stopped export/reset/restore/reexport content-hash match. It uses no real Slack export, account or host fetch and makes no source-parity claim.

The owner-only `/imports` wizard uploads a local ZIP. It suggests existing-account associations by trimmed, NFC-normalized, case-insensitive email. Every actor supplied in users.json requires an explicit decision, including ambiguous, unknown-email and unmapped actors. Bot/app identities also come from source bot profiles or named bot posts. Bots and apps always remain external even if the submitted review associates them with a Nook member. Their names come from the source, never an invented local account. A bot may override its display name per post; those names are retained while its source bot ID stays stable. A message actor absent from users.json blocks its selected channel; the importer never invents an actor object. Existing guests can be chosen only through the same explicit destination membership review; the corresponding product scope is created with that new private channel. Associations are source provenance, never native authorship, account activation, role or session grants. Every selected public source channel creates a new private Nook conversation with the owner's exact selected audience. The owner remains a member. Source membership does not grant access.

The supported source is `users.json`, `channels.json`, and channel folders containing dated JSON arrays of ordinary `type: message` records. Optional `groups.json`, `dms.json` and `mpims.json` produce owner-only exclusion diagnostics. Private and direct-message imports remain outside the original immutable policy. Known system notices (`channel_join`, `channel_leave`, topic/purpose/name changes and pin/unpin notices) are skipped and counted by kind in review. Ordinary messages, bot/app posts, `file_share`, `thread_broadcast` and `reminder_add` are admitted. Unknown message types or subtypes are named and block each affected selected channel. Missing source actors, invalid supplied file bytes, file-count/size violations and missing thread parents remain blocking diagnostics. Channels with no day files may be imported as empty destinations; export completeness remains unknown. A change or deletion marker blocks the affected selected channel; nested prior text is never reconstructed as current history. Any selected-channel blocker prevents the entire selection from becoming a reviewed Base plan, even if the owner accepts an exclusion digest. The wizard names affected channels and withholds Apply. The owner may deselect a whole affected channel or upload a corrected export; accepting selected-record loss is unavailable. Nonselected channels, private/DM exports, unsupported entries outside channel history and unreferenced files remain declared exclusions requiring review. Ordinary text, Unicode, whitespace, source IDs, exact timestamp strings, exported metadata, external authors and admitted parent/file bindings are preserved.

The record policy below distinguishes export documentation from event/object documentation. “Event inference” supports the fields but does not guarantee that payload in every export. Companion byte paths are a Nook convention, not a documented Slack export layout.

| Record kind or field | Import decision | Documentation status |
| --- | --- | --- |
| Ordinary `type: message` (`user`, `text`, `ts`) | Admit immutable history after fidelity checks. | Documented in the [export-reading guide](https://slack.com/help/articles/220556107-How-to-read-Slack-data-exports). |
| `bot_message`; app posts with bot identity/profile fields | Admit with external source identity and source display names; never associate with a Nook member. | Event inference: [bot messages](https://docs.slack.dev/reference/events/message/bot_message/) and [user objects](https://docs.slack.dev/reference/objects/user-object/). |
| `file_share` and `message.files[]` | Admit text and supplied attachments; absent bytes require explicit missing-file review and a visible notice. | Event inference: [file shares](https://docs.slack.dev/reference/events/message/file_share/) and [file objects](https://docs.slack.dev/reference/objects/file-object/). The subtype is retired for current event delivery but remains listed in export documentation. |
| Historical singular `message.file` | Apply the same file checks, inventory and missing-file choice; preserve the source shape. | Event inference: the [2018 file-thread changelog](https://docs.slack.dev/changelog/2018-05-file-threads-soon-tread/) documents migration from one file attribute to an array. |
| Thread replies and `thread_broadcast` | Admit with the actual source root; broadcast provenance retains the root timestamp. | Event inference: [replies](https://docs.slack.dev/reference/methods/conversations.replies/) and [broadcast replies](https://docs.slack.dev/reference/events/message/thread_broadcast/). |
| `reminder_add` | Admit reminder description as history; create no scheduled work. | Event inference: [reminder record](https://docs.slack.dev/reference/events/message/reminder_add/). |
| `channel_join` | Skip and count by kind; replay no membership action. | Event inference: [join record](https://docs.slack.dev/reference/events/message/channel_join/); also listed in the export guide. |
| `channel_leave` | Skip and count by kind; replay no membership action. | Event inference: [leave record](https://docs.slack.dev/reference/events/message/channel_leave/). |
| `channel_topic` | Skip and count by kind; replay no topic change. | Event inference: [topic record](https://docs.slack.dev/reference/events/message/channel_topic/). |
| `channel_purpose` | Skip and count by kind; replay no purpose change. | Event inference: [purpose record](https://docs.slack.dev/reference/events/message/channel_purpose/). |
| `channel_name` | Skip and count by kind; replay no rename. | Event inference: [rename record](https://docs.slack.dev/reference/events/message/channel_name/). |
| `pinned_item` | Skip and count by kind; replay no pin operation. | Event inference: [pin record](https://docs.slack.dev/reference/events/message/pinned_item/); also listed in the export guide. |
| `unpinned_item` | Skip and count by kind; replay no unpin operation. | Event inference: [unpin record](https://docs.slack.dev/reference/events/message/unpinned_item/); event delivery scope does not establish public-export presence. |
| `edited` snapshot metadata | Retain current text with “edited in Slack”; invent no earlier version. | Documented in the [export-reading guide](https://slack.com/help/articles/220556107-How-to-read-Slack-data-exports). |
| `reactions` | Display read-only counts and available source names; create no native reaction. | Documented in the [export-reading guide](https://slack.com/help/articles/220556107-How-to-read-Slack-data-exports); listed users may be incomplete. |
| Source user mentions in `text` | Display imported source names; create no native mention or notification. | Event inference: [message formatting](https://docs.slack.dev/messaging/formatting-message-text/). |
| `message_changed`, `message_deleted` | Block the affected selected channel; unresolved mutations are not reconstructed. | Documented message events: [message reference](https://api.slack.com/events/message); event documentation does not establish a recoverable export revision log. |
| Other unsupported kinds, including archive/unarchive, group variants and retired `reply_broadcast` | Name the type/subtype and block the affected selected channel. | The [message reference](https://api.slack.com/events/message) lists additional subtypes and marks `reply_broadcast` retired; documentation alone does not confer importer support. |
| Unknown type/subtype, including synthetic `future_unknown_record` | Name and refuse per affected selected channel. | Unknown refused: no reviewed Slack documentation establishes the synthetic subtype. |

Both the current `message.files` array and historical `file_share` singular `message.file` object follow the same supplied-byte and missing-file review. Original source metadata keeps its exported shape. Supplied files can use an explicit safe `local_path` under `files/` in the exported file metadata, `files/<FILE_ID>/name`, `files/<FILE_ID>-name`, or `files/<FILE_ID>`. Multiple matching paths are refused as ambiguous. Missing file bytes initially block readiness. The review shows each missing filename, source channel, message key and size, plus the missing reference count, total known source size and number of unknown sizes. The inventory digest is part of the reviewed plan; durable summaries retain its hash rather than filenames after erasure. The reviewer can supply bytes or explicitly select **Import without these missing files**, then preview again. Only that explicit choice admits each original message with a visible `file not supplied: <name>` notice. Supplied files remain downloadable; absent files never become fake attachments. The wizard never fetches Slack links. Supported supplied media are nonempty UTF-8 plain text, PNG, JPEG and PDF; matching signatures are checked for PNG, JPEG and PDF. If a source size or SHA-256 is declared, it must match supplied bytes. Each supplied attachment must be nonempty and at most 1 MiB. The combined `message.files[]` and singular `message.file` references count toward the five-per-message limit even when bytes are missing. A missing reference with a declared source size over 1 MiB may be admitted only after explicit missing-file acceptance, with no bytes admitted; supplied bytes that are invalid, unsupported, mismatched or oversized block review and cannot be treated as absent. The parser, source-to-Base mapping, actual D1 target admission and offline archive validation enforce the reference-count rules; supplied bytes also meet the size bound during custody staging. Native live attachment limits are separate. All admitted file metadata and bytes remain bound to their original message; every reference has either supplied bytes or an explicitly reviewed missing-file notice.

Archive admission is bounded to 32 MiB uploaded bytes, 16 MiB per inflated entry, 64 MiB total inflation, 5,000 entries and a 200:1 entry expansion ratio. Actual output size and CRC are checked. Supported ZIP methods are stored and raw deflate, with optional standard descriptors. Encryption, ZIP64, multiple disks, symlinks/special entries, absolute/traversal paths, ambiguous Unicode aliases, duplicate paths, local/central mismatches, overlaps, unexplained bytes and malformed UTF-8/JSON are rejected. JSON duplicate keys, excessive depth and unsafe integer metadata are rejected. The parser works in memory and never extracts an untrusted path to disk. The Base planner and real D1 creation preflight additionally bound reviewed plans; this is not an unlimited-archive claim.

To prepare companion bytes on your own computer:

```sh
node scripts/slack-files.mjs export.zip supplied-files
```

This is list-only: it prints each unique file reference's name, size and link host, never a full link or query, and makes no request or output directory. Valid bytes already embedded at any accepted importer path are reported as `supplied`; they are not fetched or copied into a competing output path. Invalid or ambiguous supplied bytes are refused. For references still missing bytes, supply them under `supplied-files/files/FILE_ID-name`, or explicitly request authenticated fetching:

```sh
node scripts/slack-files.mjs export.zip supplied-files --fetch --token-env MY_SLACK_DOWNLOAD_TOKEN
```

`MY_SLACK_DOWNLOAD_TOKEN` is an example environment-variable name chosen by you; populate your chosen variable through your own secret tooling with a token having `files:read` and access to the files. Both flags are required. The command does not accept a token value as an argument or write it to logs or files. Fetching admits only HTTPS `files.slack.com` on the default HTTPS port, without URL userinfo or fragments. Every redirect is checked before credentials are sent; other hosts, wildcard subdomains, HTTP and nondefault ports are refused.

The helper shares the importer's ZIP admission limits above: 32 MiB archive, 16 MiB per inflated entry, 64 MiB total expanded/source-plus-companion bytes, 5,000 entries including directories, and 200:1 entry expansion. New companion files and a new `files/` directory count toward the entry budget. Each fetched file is limited to 1 MiB, and consumed bytes from each successful HTTP response cannot exceed 1 MiB even without Content-Length. The combined `message.files[]` and singular `message.file` references are limited to five per message, including missing references; `--fetch` refuses a missing reference whose declared size is above 1 MiB. Rebuilt ZIPs must still meet the compressed archive limit.

Rerun the same fetch command after interruption. Completed downloads are checked against their SHA-256 receipts and declared source size, then skipped as `verified-existing`; the interrupted current file restarts from byte zero. Keep the helper's `.slack-files/` receipts beside `files/` for verification. Changed or unverifiable existing output is refused instead of overwritten. The helper leaves the original export unchanged. If companion files were produced, add only their `files/` folder to a copy of the original ZIP, then upload the copy:

```sh
cp export.zip export-with-files.zip
(cd supplied-files && zip -r ../export-with-files.zip files)
```

Do not add `.slack-files/` to the ZIP or add a second path for an already-supplied file. If every file is already supplied, use the original ZIP without this copy/add step. Alternatively, explicitly choose **Import without these missing files** in the wizard and preview again to bind the filename notices to the plan. Review current audiences, actor decisions and exclusions before applying. Ordinary ZIP parsing, review and apply make no source requests.

For an owner rehearsal, inspect history, search and current member access before adding live posts or changing members, then use **Undo this import** while its guard permits reversal. Later native work, changed audiences or dependent references prevent undo. Discard an unused upload with **Discard unused raw upload**; after successful reversal, use **Release upload for a fresh review** and **Finish pending file cleanup** as needed. Active import custody cannot be discarded.

Only a capture without selected-source blockers can reach Base planning. The source digest, all review decisions (including unused actor mappings and the missing-file choice), system-notice counts, missing-file totals, accepted exclusion digest, and current operator-version snapshot bind the reviewed Base plan. Changing any decision requires a fresh preview. The application uses Base's actual asynchronous `modules/import-kit/src/d1` engine for persisted jobs, source identity claims, provenance, atomic native effects and checkpoints. Exact retry recovers the same operation receipt. Cold resume requires the retained plan and current authorization, not a browser-held cursor. Each batch rechecks current operator/session/owner authority and exact destination membership in SQL before and after its writes. Stale plans and changed source identities refuse; there is no automatic changed-source reconciliation or existing-channel merge.

Historical messages use normalized immutable import records, bounded normal channel history windows and ordinary indexed search. Display positions are negative and native events remain positive; imported positions never advance read/replay/unread state. Source threads and broadcast replies retain their original roots and remain read-only. A broadcast retains the parent timestamp instead of duplicating the parent body inside its provenance, so later erasure cannot leave a second copy. Reminder descriptions are ordinary immutable history and never schedule native reminders. Source user mentions display the imported source name, without creating native mentions. Reactions display exported counts and available reactor names as read-only history. Current exported edited text is retained with an “edited in Slack” marker; prior nested versions are not reconstructed. Their author remains an external source identity. They create no live events, unread activity, attention, mail, fanout, decisions or accepted commitments. File bytes use the product's real R2 binding and durable object-deletion queue. Raw ZIPs, excluded private bytes and detailed reports stay in owner custody. There is no automatic raw-upload expiry; the wizard provides explicit disposal of an unused upload and rejects disposal of active import custody.

Undo is owner scoped and uses Base's guarded reversal. It refuses later live work, changed audiences, changed native state or later references. Cleanup deletes only the import's owned records/files/conversations and leaves a durable object cleanup queue if object-store deletion fails. Historical record editing remains unavailable. A reader's operator-version change blocks forward apply/resume but keeps the current owner's job status visible. When the exact channel audience and native history remain unchanged, the owner can roll back a partial import or undo a completed one, then use **Review this upload again** to bind a fresh current-authority approval. Old reviews and plans remain immutable. A replacement approval waits for the old product cleanup to finish and receives distinct per-review file custody whose bytes must match the retained ZIP. Retrying an old rollback or a delayed old file deletion cannot remove the replacement's rows or files. A deactivation that changes the audience still blocks destructive cleanup; administrators have no override.

D1 refuses a Worker invocation's statement after its 1,000th, so every import request keeps within 900 statements counted at the binding: the sign-in check, Nook's own reads and writes and Base's batches together, with 100 left as margin. Apply first stages the export's files in owner custody, at most 100 files per request, and creates the Base job once all are ready; the wizard repeats apply until then, and **Apply reviewed plan** continues it after an interruption. Base's batches take what each request has left. The request that finishes undo deletes as many of the import's file objects as its remaining budget allows and wakes the workspace hub, whose alarm drains the rest of the deletion queue.

No storage migration is needed: existing source JSON, immutable plans and attachment bindings carry the additional source formats and missing-file declarations. Previously applied ordinary imports retain their original plan encoding and mapping version; the recovery reader accepts those original plans without rewriting their fingerprints. Offline restore requires every completed Slack review to retain its completed Base job, exact canonical plan and original capture, publication provenance, source claims, entry receipts, native effect revisions and matching product rows/files. Unapplied reviewed/discarded drafts may have no Base job; undone reviews retain a terminal Base job and cannot own live domain rows. The existing portability flow exercises genuine Base export, archive reading, staging and finalize, including rejection of resealed missing-job/plan/provenance states without restoring any rows or provider bytes. Fixed DM rosters retain inactive historical participants and are subject to the same maximum membership as normal creation.

The large source/planner fixture has 1,205 messages across two channels and 205 actors, including six replies. These counts describe fixtures, not hosted capacity.

It proves explicit missing-file choice, supplied files beside missing ones, bot display overrides, mentions, edited markers, read-only source reactions, quiet native tables, restored guarded undo, resealed choice tamper rejection and erasure of missing-file names and duplicated broadcast-root text.
