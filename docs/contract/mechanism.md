# Nook contract mechanism and compatibility

Product obligations and status are in CONTRACT.md. These notes retain technical protocols, limits and legacy recovery details moved out of clause bodies.

## NOOK-009

Two full backup paths ship, neither an ordinary app-admin export. On a local install, the filesystem operator uses local-only `rer export` and `rer import` on a stopped checkout; operator disk access explicitly bypasses app privacy. For a hosted install, the [hosted backup/export path](docs/backups.md#export-a-hosted-nook) uses the owner’s `/export` download or the documented `node --input-type=module` command calling `scripts/local/remote-export.mjs` from a checkout with dependencies installed; it exports the authoritative D1 database records and actual private R2 object bytes into an owner-held verified archive with its erasure journal. Nook's `/export` and `/api/portability` doors admit only an active owner's current session and authorize no import. [Base's hosted-data rule](https://github.com/runeditrun/base/blob/main/export/RUN-LOCALLY.md#if-hosted-deployment-stops) distinguishes this from local-only `rer export`, which refuses a hosted origin: a platform D1 SQL export alone omits R2 files and cannot satisfy this full-backup guarantee. Restore is always local, into an empty destination, and validates table identities, foreign references, schema ledger and event/read frontiers. Archives exclude sessions and sign-in tokens. User-readable and policy-scoped exits are required by NOOK-047; this clause retains the full-backup guarantee and its explicit operator-custody exception.

**Local:** Stop the install, export with `rer export`, import into an empty stopped local install, complete explicit identity recovery and re-export; compare equivalent records, private media bytes and erasure journal.

**Hosted:** Sign in as an active owner, follow the hosted backup/export path through `/export` and the documented helper command to download D1 records plus R2 bytes into an owner-held archive, import it into an empty stopped local install and complete identity recovery; compare records, file bytes, rebuilt search and erasure journal.

## NOOK-012

Attachments are 1 byte–25 MiB per file, five ordered files per message, with at most 50 pending/staged native uploads per uploader and no aggregate workspace byte quota. Actual bytes reside in private R2; D1 holds metadata and opaque object keys. Plain UTF-8 text, signature-checked PNG/JPEG/PDF only; forced attachment downloads plus private inline PNG/JPEG previews after structural byte validation and opt-in plain-text previews bounded to 64 KiB; no inline PDF preview or virus-scanning claim. Staged uploads last24h for binding/read eligibility, are uploader-only under current conversation ACL, and do not create attention. Unused staged bytes remain until explicitly removed. Binding uploader-owned same-conversation IDs and message/intent/event is atomic; exact ID order belongs to retry identity. Downloads recheck current membership; delete erases live bytes/name/checksum, and message deletion cascades. The media baseline archivev2 carries actual bytes plus hashes, state and binding; historical archivev3 retains these guarantees plus C13 triage and supports explicit prior-v1/v2 migration; current normalized Base portability archives retain the same custody guarantees, as described below. Backups/WAL/remnants retain their stated physical-erasure limits. These limits are the shipped baseline, not the target: NOOK-061 widens admission to any file type up to 1 GiB with in-app previews, malware scanning and admin file-type policy while keeping every custody guarantee in this clause.

## NOOK-013

Calm attention is explicit per-user triage, independent of unread and outcome authority. GET/PATCH `/api/conversations/:id/preferences` accepts boolean `muted`/`followed`, requires current membership, and returns those choices plus followed root-thread IDs. POST `/api/messages/:id/follow {follow:boolean}` targets a live root thread under current ACL. Choices persist across sessions; changes affect future routing only. Muting suppresses routine follows, never explicit mentions or commitment proposals. Automatic following when a member authors, replies in or is mentioned in a thread, and of every thread in a one-to-one DM, is NOOK-072 and writes this same followed state; an unfollow through this door also ends an automatic follow.

Message sends accept ordered unique `mentions` (at most50 current member IDs), boolean `urgent`, and `urgentReason` (1–240 characters when urgent). Urgent requests require explicit recipients. All current channel members can see the message's Notified names, Urgent marker and urgent reason, including members who were not notified. Defaults `[]`, `false`, `null` join immutable intent identity. Identical committed retries survive recipient removal without rerouting; new sends revalidate recipients. Attention creation is atomic with durable message/outcome events and stores opaque references, not copied bodies. Precedence: urgent-request, mention, thread-follow, conversation-follow. Proposals and material revisions route to assignees; assignee actions route updates to authors. Self-authored events do not create self-attention.

GET `/api/attention` returns current-ACL hydrated active items, `deferredCount`, `dndUntil`. Deleted sources hydrate tombstones, with no urgent-reason copy. GET/PATCH `/api/settings {dndUntil:epochMilliseconds|null}` controls quiet time. Quiet time defers routine items while urgent in-app requests remain visible; external delivery follows C14 email and C15 Web Push, and there is no paging guarantee. POST `/api/attention/:id {action:done|snooze,until?:epochMilliseconds}` requires item ownership and current ACL. Quiet/snooze deadlines must be future times within seven days. Snoozed items become eligible when due; routine items remain deferred during quiet time. Done changes only triage. Reading or accepting a commitment does not automatically close attention, and closing attention never accepts work.

Schema5 preserves prior ledgers and appends explicit defaults to live prior intent payloads; erased markers remain erased. Archivev3 retains follows/preferences/quiet time/triage and validates source/event/scope references. Explicit v1/v2 imports add empty attention tables and normalize prior retry identity. Old-format archives cannot carry nonempty new attention state. Root SQLite v3 and native D1 recovery formats require an explicit separately verified mapping; a source manifest alone does not establish compatibility.

C13 admission clarification: defaults apply only to omitted mentions/urgent fields, not explicit null. Explicit mentions:null or urgent:null is400 with no committed event/message/attention. Recovered dnd_until must be null or a safe integer; expired valid integers remain legal recovery values. Quiet-time domain checks precede database insertion.

Automatic follows from authoring, replying, mentions and one-to-one DMs are proved under NOOK-072; an unfollow through `POST /api/messages/:id/follow {follow:false}` ends one.

## NOOK-014

Email notifications reach a member away from the browser under this delivery contract. Emailable events are an explicit mention, an urgent request, a commitment proposal or material revision to its assignee, and a completion report to its author; routine thread or conversation follows, reactions, replies without a mention, accept/cancel updates and imported history are never emailed. The destination is the member's own sign-in email (an active account, verified by its sign-in link); there is no free-form address. Every member's email is off until that member turns it on in their own settings, per account: one choice covers mentions and commitments, a second covers urgent requests, with a separate choice to let urgent requests through quiet time. GET/PATCH `/api/notify {mentions,urgent,urgentQuiet:boolean}` reads and changes the caller's choices. Turning a choice off stops the next email: each queued item is checked again when its email is built. Every email carries a link that turns email off without a session (`/notify/off`: opening it shows one button and changes nothing, because mail scanners open links; the button turns all three choices off) and a link to the signed-in settings.

Queue rows are written in the same batch as the attention rows, only for recipients who turned the matching email on, and hold opaque references (recipient, conversation, actor, message or commitment, reason), never message text, file names or addresses. The ChatHub alarm drains them; pending rows keep it armed, so delivery needs no open socket and a restarted Worker resumes from D1. When an email is built, nothing is sent to an inactive member, about a conversation the member can no longer read, about a deleted or erased source, after the choice was turned off, or for an item the member already marked done or a mention they already read; each is canceled with that reason. Quiet time (C13 `dndUntil`) holds every item until it ends; an urgent request goes through quiet time only when its recipient chose that. Each event is queued once per recipient (keyed by its attention item), so identical retries add nothing; a burst within five seconds folds into one email, and a recipient gets at most one email per conversation per ten minutes, with later items folded into a count. A failed send is retried after 15 s, 1 min, 5 min, 30 min and 2 h, then given up; a definite refusal is not retried, and a send the provider did not confirm, or that a stopped Worker may have made, is never repeated. A send being retried or given up shows as "email not delivered" with its reason class (not set up, refused, rate limited, not confirmed) to its recipient, to the member whose message caused it and to the owner for seven days, never as a silent success. Emails name the sender, the conversation (`#name`, or "a direct conversation") and a link; they never carry message text, file names, urgent reasons or commitment wording. This no-text form is today's behavior and the `sender` level an owner policy can force; a member's opt-in to message text in email is NOOK-062's obligation.

Hosted mail goes through the same configured sender as sign-in (the owner deployment's provider). Local development sends and stores no email and exposes no mail viewer. Tests fake only the provider network edge. Accepted by the mail provider is not proof of inbox receipt, and a test provider's acceptance is not live delivery. Urgent stays an in-app request, not paging; Web Push follows C15; there is no SMS or native push. Archives carry members' choices but not the queue, so a restore sends nothing old; erasure removes a member's choices and queued items and an erased message's items.

## NOOK-015

Execution: `pnpm test:push` runs subscription/preferences, the emitted Worker and the real alarm. `tests/push-journey.mjs` and `tests/push-clock.mjs` provide this local evidence; provider-edge acceptance and real-device display remain separate proof.

Web Push is a separate opt-in channel under C14's current-identity, current-ACL, source, read/done, quiet-time, retry, visible-failure and no-paging rules. Migration 0023 preserves existing email rows and choices. **Defaults for a new member:** once the member grants browser notification permission, and without opening settings, DMs, mentions (including NOOK-065 broadcast mentions), keyword hits (NOOK-032), call invites (NOOK-022) and replies in followed threads (including NOOK-072 automatic follows) are on, matching Slack's default of desktop and mobile notifications for DMs, mentions and keywords; urgent-through-quiet starts off. Each member may change any of them, and owners set the organization defaults under NOOK-060. GET/PATCH `/api/notify` adds `push:{mentions,urgent,urgentQuiet,direct,threads,keywords,calls:boolean}`. Mentions covers the same commitment events as email. Ordinary DMs and followed-thread replies can push without changing email or in-app Attention. Conversation-follow for Attention alone never pushes; only a conversation set to the NOOK-100 `all new messages` level pushes each new root message and channel-broadcast thread reply. Explicit urgent and mention reasons take precedence and require their own choice; a routine followed reply precedes ordinary DM when both are enabled. Routine follows and DMs respect mute; self-authored and imported events never push.

POST `/api/devices {transport:"webpush",subscription:{endpoint,keys:{p256dh,auth},expirationTime?:number|null}}` registers only the caller's browser subscription under the current session. GET returns only the instance VAPID public key and the caller's opaque device IDs, transport and timestamps. DELETE `/api/devices {id}` removes only an owned device. Endpoint ownership cannot transfer between accounts: unsubscribe in the browser before enabling another account. At most ten devices per person; HTTPS endpoints are restricted to the supported Apple, Google and Mozilla push hosts, keys must be valid P-256/16-byte material, redirects are refused. This browser door accepts only `transport:"webpush"` and rejects every other transport; native iOS and Android devices register their APNs, PushKit or FCM tokens through the native device door and push path that NOOK-078 defines, and desktop apps receive over their own authenticated connection to the installation. Web Push needs no publisher service: each installation signs with its own VAPID key and sends straight to the browser vendor's push service. Each delivery rechecks the device's original session, active version, membership, preferences, native source and unread/triage state. Expired or revoked sessions and provider-expired subscriptions retire the device.

One durable queue row per event, recipient and device prevents duplicate alerts from overlapping reasons and successful-device repeats during another device's retry. Email and push have independent five-second gathering and ten-minute conversation folding windows; push windows are per device. The first due eligible item gathers the already-queued eligible burst, including items still in their initial gathering period; future retries, snoozes and quiet-held items stay deferred. A counted push uses one opaque delivery ID for the whole burst, and remains current while any folded item remains current. A conditional sending lease becomes visibly not-confirmed if interrupted, and uncertain network sends are never repeated. Failure classes show to the recipient, the sender and the owner for seven days; terminal delivery queue rows last thirty days, while NOOK-073's held, released and canceled routing records are retained as that clause states. Read and done transactions cancel pending push. Snoozes and quiet time defer delivery; only the separately enabled urgent-through-quiet choice overrides quiet time.

POST `/api/devices/presence {id,page,visible:boolean}` records a current-session visible-page heartbeat. Visible presence alone holds no Web Push; NOOK-073's cross-device active-elsewhere rule governs Web Push exactly as native push: a focused page with recent input is an active desktop client, Web Push to the member's phones and tablets is held while they are active on desktop and released or canceled under NOOK-073, and the active client itself shows the alert in-app. Open sockets alone never count as presence. Foreground pages renew every fifteen seconds, hidden pages release, and the alarm automatically releases expired forty-five-second presence. No browser page is needed for delivery. GET `/api/devices/sync` supplies current opaque delivered-notification IDs and badge count for foreground synchronization; the count includes unread active attention and ordinary push-enabled DM events, deduplicated across devices.

Web Push uses RFC 8291 encrypted payloads and RFC 8292 VAPID. The instance generates its key pair once on first authenticated use, storing the private key AES-GCM encrypted under a key derived from SESSION_SECRET, and sends only its public key to browsers. The encrypted payload contains sender/conversation display wording (DMs use "a direct conversation"), an authenticated same-origin app link with opaque conversation/message IDs, opaque recipient/delivery IDs, notification tag and badge count. No message body, commitment text, urgent reason or file name is included; this is the `sender` preview level, and NOOK-062 adds default-on message-text previews (inside the same encrypted payload), org caps and notification actions. Push services see the endpoint, timing, encrypted packet size, TTL/normal urgency, VAPID public key and signed audience/expiry/contact URI. Subscription endpoints, public encryption keys and auth material remain private D1 records. Archives exclude keys, devices, presence and the live delivery queue; NOOK-073's body-free routing records travel in operational archives as history and are never sent, so restored installations send nothing old. Member/message/outcome erasure removes associated push records: the erased member's devices, presence, preferences, queue rows and routing records, and every recipient's queue rows and routing records of alerts the erased member, message or outcome caused. Logical erasure cannot retract packets already accepted by a push service or notices already displayed on a sleeping device.

The installable PWA preserves Nook's UI and authenticates navigation on every notification tap. Its service worker caches no requests or private content. Permission requests require a gesture; the foreground reconciles allowed subscriptions and visibly reports re-enable failures. The previous open-tab OS notification path is removed; the title count remains. Every Web Push shows a visible notification and can update its badge. No badge-only or clear-only background Web Push is sent: WebKit revokes silent subscriptions. Foreground authoritative refresh closes read/revoked notices and updates badges through the service worker. Immediate clearing on a sleeping device, native iOS badge updates and Android native normal-priority clears remain blocked until a native transport exists. Browser acceptance is not proof of OS receipt; C8's evidence limits still apply.

**Defaults:** a newly invited member grants browser permission in a fresh profile without opening settings, and a DM, a mention and a keyword hit each show exactly one notification; a channel set to `all new messages` notifies on a colleague's plain message and a channel left at `mentions` does not.

**Defaults include automatic follows:** a reply in a thread the member started in a `mentions` channel shows one notification without any explicit follow.

**Cross-device routing:** with the member's Chrome page focused and in use, a DM shows on that page and no Web Push reaches their phone's installed PWA; after the page is idle 10 minutes the phone notifies (NOOK-073).

## ERASURE-001

Current owners/admins may erase accessible channel messages; roles never open an operator DM door. Authors retain their own delete/remove actions. Owners may erase eligible other members; admins only accounts with the member role, including guest access; self and the last active owner are refused. Every destructive commit guards current session, role and scope. Count-only preview, explicit confirmation and a subject-free receipt accompany operator erasure. Authored content, credentials and selected import copies are erased; authored work retains only scope/kind/version count/state. Other authors retain work and state without erased assignee/action attribution. Shared conversation notes are such work: member erasure removes only the member's author, reviser and pin attribution, and a note another member authored or revised keeps its title, text, checklist items, links, pin state and every snapshot for the other participants; notes the member wrote alone, and notes on the member's erased thread roots, are cleared (NOOK-053). Web Push routing records are removed with the member they belong to and with the message, outcome or member that caused them (NOOK-015, NOOK-073); none is a structural tombstone. Separate credential-free structural tombstones preserve threads, counters, fixed DM audiences and immutable import ownership; audit attribution and subject references are independently anonymized. D1 atomically records public Base erasure fences and durable blob obligations before R2 deletion. Completion requires verified blob absence, including resolution of uncertain puts; larger work remains pending with bounded continuation. Latest archives carry the journal and restore normally. Old archives are refused by nonempty-destination guards or the latest journal; a virgin destination without a later journal cannot recognize them. External archives, offline copies, provider backups/Time Travel and physical remnants remain outside logical erasure.

## NOOK-032

Extend per-conversation mute/follow and one-off quiet time with recurring working/quiet hours in the recipient’s time zone, weekday exceptions, vacation and device-specific rules; when the member's phones and tablets alert relative to desktop activity is NOOK-073. Members choose mentions, DMs, followed threads, digests and whether explicit urgent requests may bypass quiet time. Activity feed, badges and external channels reconcile read/done status without turning a mention into an obligation. Members define personal keywords (words or phrases, case-insensitive, token-matched like NOOK-019) that create a `keyword` Attention reason with its own push/email choice, only in conversations they can currently read, never for their own messages and not in muted conversations unless chosen. Explain why each item was delivered, held or suppressed and allow a bounded snooze; DST and travel do not silently shift the declared schedule. **Per-conversation notification level:** each member sets any channel, private channel, shared channel or group DM to `all new messages`, `mentions` or `nothing`, with an optional different level for mobile devices (phones and tablets) than for desktop and web. `mentions` is the default for channels; one-to-one and group DMs default to `all new messages`. `all new messages` creates a routine `all-messages` Attention reason and alerts the chosen device class on each new root message and each thread reply also sent to the channel (NOOK-117), under the member's quiet schedule, NOOK-097's delivery bar, NOOK-062 previews and the NOOK-014/NOOK-015 gathering and ten-minute folding rules; the member's own and imported messages never alert. `mentions` alerts only on explicit mentions, NOOK-065 broadcast mentions, keyword hits, urgent requests and followed-thread replies (including NOOK-072 automatic follows). Alongside the level, a member may set **all thread replies** for the conversation (NOOK-122), so every thread in it counts as followed for them, with its own mobile override. `nothing` sends no device or email alert for that conversation, including `@channel`, `@here`, `@everyone` and explicit mentions, consistent with NOOK-065's ignore choice; explicit mentions and urgent requests still appear silently in Attention. `all new messages` and NOOK-013 mute are exclusive: choosing one clears the other. A settings list shows every conversation whose level differs from the default (per device class), and each row resets to the default in one action. The level is served through `GET/PATCH /api/conversations/:id/notify {level, mobileLevel, threads, mobileThreads}` and every client. **New-member defaults:** push alerts on DMs, mentions, keyword hits, call invites and followed-thread replies, including NOOK-072 automatic follows (NOOK-015, NOOK-021), routed between desktop and mobile by NOOK-073. Email stays off (NOOK-014), and first sign-in onboarding says so plainly, offering one action to turn on "Email me about mentions and DMs when I'm away" bundled every 15 minutes or hourly; owners may make that email choice on by default for new members under NOOK-060. Keyword hits, quiet schedules and previews inherit NOOK-072's thread-follow sentences that name this clause.

Web quiet schedules keep seven weekday rules in the recipient’s explicitly chosen IANA time zone, initially using their profile zone. An overnight rule belongs to the day it starts; disabling Friday leaves Thursday night’s Friday morning intact. Each boundary is resolved from its local calendar date: overlaps use the earlier occurrence and missing local times advance by the transition gap. The stored wall-clock times and zone stay unchanged through DST and travel; time-zone changes are explicit. Email and Web Push hold and release through the existing durable queue, recheck current access and notification choices, and retain the existing opt-in urgent bypass. Quiet and item snoozes are bounded to seven days. Attention and the recipient-only delivery view explain delivery, quiet holds, level suppression and active-elsewhere holds; provider acceptance does not claim observed device display. Web Push quiet-schedule and quiet-snooze holds, and their releases, are retained with their hold reasons as NOOK-073 routing records; email entries follow NOOK-014. The schedule survives archive restore, with derived boundaries recomputed, and follows member erasure.

## NOOK-041

Import official Slack export ZIPs within the exporter’s actual authority, including public/private channels, one-to-one/group DMs and shared-channel history where supplied. Preview identities, memberships/audience, date coverage, messages, threads, reactions, edits/deletions, pins/saves, bot provenance and file bytes/references with explicit unsupported/missing accounting. Map identities and private audiences deliberately, never by display-name collision. Fetch permitted files using a scoped approved source grant or supplied bytes; list inaccessible files and require a reviewed disposition. Resume/dedupe by source identity, reconcile every record and retain immutable provenance. Imported history creates no unread, notifications, bot/workflow runs or accepted work. Guarded batch undo preserves later native discussion. The preview lists every app, bot, incoming webhook, slash command and workflow found in the export (`integration_logs.json`, bot messages and bot profiles, and workflow data where supplied) with its Nook disposition: repoint to a NOOK-063 Slack-compatible webhook or NOOK-112 Web API app (issuing the new URL/token), replace with a named first-party connector (NOOK-027–030), replace with a NOOK-064 Zapier/Make/n8n path, rebuild as a NOOK-026 workflow, or unsupported with its reason. Cutover yields an owner checklist and no integration is silently dropped. Source export-plan restrictions are shown, never solved by making private content public. **Consented member source for what the export omits:** Slack's official export on Free and Pro plans contains public channels only (private channels and DMs need Business+ after applying, or Enterprise), so for every conversation the supplied export does not include, each member may sign in to Slack through Nook with a user-token OAuth grant limited to reading their own history (`groups:history`, `im:history`, `mpim:history`, `files:read`, with `users:read` for identity mapping), shown before consent with exactly what will be read. Nook fetches only the private channels, DMs and group DMs that member belongs to (`users.conversations`, `conversations.history`/`replies`, file bytes through that token) into a staged preview that only that member can see; no owner, admin or other member reads staged content, and an admin role never consents for anyone. A staged conversation is published to its Nook audience only when its audience rule is met: a 1:1 DM or group DM needs every participant's consent (their own grant or an in-Nook consent on the staged item); a private channel needs its Slack channel manager's consent or, where none is in Nook, the member quorum the owner states before the run (default: a majority of its current members) with no explicit objection; and it imports to exactly its Slack membership through reviewed identity mapping. File bytes, threads, reactions, edits/deletions, provenance (`slack-member-grant` and the granting member), resume and dedupe by source ID (overlapping fetches from several members yield one record), inert import and guarded batch undo apply exactly as for the export. Revoking a member's Slack grant, in Nook or at Slack, stops further fetches with that token at the next request; already published conversations stay, and that member's unpublished staged items are erased unless another consenting member's grant covers them. Staged content that never reaches its audience rule is erased after an owner-set window (default 30 days). The cutover report lists every conversation not imported by type, member count and missing consents; nothing is silently dropped. Through the owner's approved source grant, custom emoji (`emoji.list` with image bytes and aliases) and user groups (`usergroups.list` and `usergroups.users.list`) are imported so custom-emoji reactions render and `@group` mentions map to Nook user groups (NOOK-065). **Cutover invitations:** the cutover preview lists every active Slack member from the export's `users.json`, or from the owner's approved source grant with `users:read.email` where the export lacks addresses. Each row shows the Slack user ID, email, name and a proposed Nook role. Full members are proposed as members, and Slack Workspace Owners and Admins are flagged so the owner may choose admin; admin is never granted without that explicit choice. Multi- and single-channel guests (`is_restricted`, `is_ultra_restricted`) stay guests limited to their mapped channels. Deactivated users (`deleted`) and bots get no invitation, while their history still imports under their reviewed identity. A member with no address is listed as needing one, never guessed. After editing roles, the owner sends every invitation in one reviewed action, now or at a chosen cutover time that survives restart. Accepting an invitation claims that person's imported authorship through the reviewed Slack-user-ID mapping recorded on the invitation, never by display-name match, and opens the consented member source to them. The cutover report shows invited, joined, pending and bounced counts per role and resends pending invitations in one action. Joining changes no private channel or DM audience, and invitation emails carry NOOK-126's code, open-in-app link and QR code. Slack Connect participants from other organizations are not in `users.json`; their channels and external DMs get their own preview, dispositions and report under NOOK-076. **Personal setup:** through a member's consented grant, Nook also imports what Slack lets that member read for themselves: their reminders (`reminders.list`, `reminders:read`) as NOOK-033 reminders (future ones fire at their time, past ones import as completed) and their starred items (`stars.list`, `stars:read`, where Slack still returns them) as NOOK-020 saved items, visible only to that member. Onboarding and the cutover report state plainly which personal setup Slack gives to no export or API and must be set again (sidebar sections, per-channel notification levels and mutes, scheduled messages, and saved "Later" items the API does not return), with a checklist linking each to its Nook setting. **Slack links in imported history:** every Slack message permalink (`https://<workspace>.slack.com/archives/<channel>/p<ts>`, with or without `thread_ts`), `slack://` link and `<#C…>`/`<@U…>` reference in imported messages, pins, bookmarks, topics and purposes is resolved through the import's Slack-ID map and rendered as the Nook permalink of the imported message, thread, channel or person; the original URL stays in provenance and the imported revision is unchanged. A link whose target was not imported, or whose target the reader cannot currently read, renders as "Slack message not imported" (or "Not available to you") with the original URL and never reveals the target's content, name or audience. A Slack permalink pasted into Nook after cutover resolves the same way under the reader's current ACL, and the cutover report counts resolved and unresolved links. **Final catch-up:** everything posted, edited, deleted or created in Slack between the first import and the switch is brought across by NOOK-077's delta passes; the cutover time above runs NOOK-077's final pass before the invitations are sent, and the report states the time through which Slack history is imported.

## NOOK-051

Keep a durable, access-controlled audit of sign-in/session changes, invitations, roles, membership, app/agent grants, workflow runs, exports, holds, policy changes and destructive actions, including actor/service, time, scope, version, reason and outcome without private bodies or secrets. Audit cannot be edited by the subject; erasure anonymizes attribution without destroying count/time facts or policy-required preservation. Authorized admins filter/export the log, and automation links each proposed/performed action to its source, grant and human approval. Failed/uncertain actions remain distinct from confirmed effects. It inherits the labeled admin-override posts and channel posting-permission changes of NOOK-066 into this log.

Web semantics: owners and admins read, filter by actor, kind, scope, outcome and time range, and export CSV or JSON; the owner alone reads when no admin exists, and members and guests never read it. A direct-conversation event shows only “a direct conversation” and counts; a private channel uses the label already shown in channel action history. No message body, DM content, credential or token value is copied. Integration tokens are named by their label; tokens and bindings are excluded from archives and reissued after restore (NOOK-079). An accepted export starts uncertain and stays uncertain if interrupted or cancelled; only a committed complete job confirms completion. Failed source actions remain failed. The reason names the operation or policy choice; versions use the recorded source version or generation, export revision plus one, and audit format version 1 for versionless sources. Older mutable records carry their recorded creation or preparation time, never a reconstructed transition time; rows without a timestamp use migration observation time. The subject has no log-edit door. Erasure sets actor to null while counts, time, scope, version, reason and outcome survive, including readable workspace exports and operational archive restore. Existing web writes carry their human actor or named service and source record; NOOK-080 notification apps now link their channel approval and app identity in the same write batch. Other app, agent and workflow execution linkage remains under the named clauses. App and agent grants and runs (NOOK-025/054/059), workflow runs (NOOK-026), legal holds (NOOK-038), SSO/provisioning (NOOK-037), two-factor changes (NOOK-069), native client sessions (NOOK-021) and connected-system actions (NOOK-027/028/029/030) each inherit: writes one audit row in the same batch, with the grant, source and human approval it links to.

## NOOK-053

### Provider request protocol and proof limits

Built: the owner's settings door (off by default, owner only, the key sealed under its own domain label, shown only as held or not and removable, the provider named as a subprocessor by host, a per-installation daily call cap in which every attempted call spends one reservation), and the request door `POST /api/clips/<id>/provider-transcript`.
